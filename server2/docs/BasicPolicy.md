# ユーザ管理 基本方針

## 1. 前提となる要件

- 依頼元の要望として、メールアドレスなど個人情報に繋がるデータはシステム内に保持しない。
- 家族で1台の端末を共有して利用するケースを想定する。
- 利用端末は、スマートフォンまたは家族共用のタブレットを想定する。
  - 端末は持ち歩いて利用されるため、通信は自宅の Wi-Fi に限らない（モバイル回線や公衆 Wi-Fi など）。
- 利用データ（テスト結果）は、退会・ユーザの削除の後も保持する（10.7）。利用データには、氏名・メールアドレスなどを含めない。
- 運用担当者や、利用者に本アプリを提供する団体などを「組織」として扱い、所属する家族の利用データを組織へ提供できるようにする（10.）。

## 2. アカウント構成

- 「家族（グループ）」と「ユーザ」の2階層で管理する。
- 認証情報は家族単位で1つにまとめる。ユーザは個別の認証情報を持たない。
- 1つの家族に登録できるユーザは1〜4名。
  - ユーザは後から自由に追加・削除・並べ替えできる。
  - ただし最低1名は残す必要がある。
  - ユーザのうち1名はスーパーユーザとする（9.3）。本登録時の1人目のユーザがスーパーユーザとなる。
- 家族は、0または1つの組織に所属できる。所属していない家族は個人ユーザとして扱う（10.）。
- 家族（アカウント）は退会できる。退会すると、家族・ユーザ（ユーザ名を含む）・端末のログイン・組織への所属が削除され、復元できない。
  - **利用データ（テスト結果）は削除せず、保持する**。保持された利用データは、運用担当者のみが参照できる（10.7）。
  - 退会は家族向けの重要な操作（9.2）とし、スーパーユーザのパスワードなどによる確認を求める。
- ユーザ名には本名ではなくニックネームを推奨する旨を画面で案内する。
- メールアドレスを保持しないため、同じメールアドレスから複数の家族が登録されても検出できない。これは仕様として許容する。

## 3. 登録フロー

### 3.1 仮登録

1. ユーザがメールアドレスを入力する。
2. 送信前に、入力されたアドレスを確認画面で表示する。
3. メールアドレスは POST で送信する。
4. サーバはランダムなトークンを生成し、以下のみをデータベースに保存する。
   - トークンのハッシュ
   - 有効期限（24時間を目安とする）
5. 本登録用URL（トークン本体を含む）を入力されたメールアドレスに送信する。
   - トークンは URL のフラグメントに含める（例：`https://<ホスト>/register#token=<トークン>`）。3.2 参照。
6. メールアドレスはデータベースに保存しない。
7. 送信完了画面で、届かない場合は迷惑メールフォルダを確認するよう、送信元アドレスとともに案内する。

- 他者のメールアドレス宛てに大量送信する踏み台にされないよう、以下を行う。
  - CAPTCHA（Cloudflare Turnstile など）で自動送信を防ぐ（主な対策）。
  - システム全体の送信数に上限を設け、急増を監視する。
  - IP 単位の送信回数制限は、緩めの補助にとどめる（4.4 参照）。
- 有効期限切れの仮登録データは、定期的に削除する。

### 3.2 本登録

1. 本登録URLが開かれたら、ページの JavaScript が URL のフラグメントからトークンを読み取り、照合用の API に POST の本文で送る。サーバはトークンをハッシュ化し、データベースと照合する。
   - フラグメント（`#` 以降）はブラウザからサーバへ送られないため、トークンが Web サーバ・CDN・プロキシのアクセスログに残らず、`Referer` ヘッダで漏れることもない。
   - 読み取ったら、`history.replaceState()` で URL からフラグメントを消す（ブラウザの履歴や画面共有でトークンが見えないようにするため）。
     - ページの再読み込みに備え、トークンはそのタブの `sessionStorage` に一時的に保持し、本登録の完了時に削除する。
   - 本登録ページには、URL 全体を外部に送るアクセス解析などのスクリプトを読み込まない（フラグメントも送られるため）。
   - 一致し、かつ有効期限内であれば、ユーザ名入力画面を表示する。
   - 照合の時点では仮登録データを削除しない。メールのリンクスキャナー（Outlook の安全なリンクなど）がURLへ自動でアクセスし、JavaScript まで実行した場合でも、ユーザが開く前にトークンが消費されるのを防ぐため。
   - ページの表示（GET）と照合の API では、データベースを変更しない。
2. ユーザ名入力画面で、1〜4名のユーザ名を入力してもらう。
3. 登録ボタンがタップ（POST）されたら、サーバはトークンを再度照合し、有効であれば以下を1つのトランザクションで行う。
   - 家族・各ユーザの識別情報を登録する。
   - この端末のセッション（認証トークンのハッシュ）を登録する。
   - 復旧コードのハッシュを登録する。
   - 仮登録データを削除する（URLは1回限り有効）。
4. 認証情報を HttpOnly Cookie で設定する。
5. 復旧コードを表示し、ユーザに控えてもらう。
   - 「復旧コードと Cookie の両方を失うと、アカウントは復旧できない」ことを明示する。

- ユーザ名入力の途中で離脱した場合も、有効期限内であれば同じURLから再開できる。
- 組織からの招待メールのURLから登録する場合は、11. を参照する（仮登録のメール送信は不要）。

## 4. 認証

### 4.1 Cookie

- 認証情報はローカルストレージではなく HttpOnly Cookie に保存する。
  - Safari の自動削除の対象外とするため。
  - JavaScript から読めないようにし、XSS による窃取のリスクを下げるため。
- Cookie には以下の属性を付ける。
  - `Secure`、`HttpOnly`、`SameSite=Lax`
  - 可能であれば `__Host-` プレフィックス（`Path=/`、`Domain` 属性なし）
- API はページと同一オリジンに置く。
  - Safari は、サイトと異なるIPのサーバ（別ドメインや CNAME で立てた API など）が設定した Cookie の有効期限を7日に制限するため。
- Chrome は Cookie の有効期限の上限が400日であるため、アクセスのたびに有効期限を延長する（スライディング更新）。

### 4.2 セッション

- サーバ側では、認証トークン・復旧コードともにハッシュで保存する。
- 認証トークンは端末（ブラウザ）ごとのセッションとして発行し、家族に複数のセッションを持てるようにする。
  - ログイン中の端末一覧の表示、他の端末のログアウトを可能にする。
- 以降のアクセスでは Cookie の認証情報で自動的に認証する。
- セッションはクライアントの IP アドレスに紐付けない（4.4 参照）。

### 4.3 CSRF 対策

- Cookie で自動的に認証されるため、状態を変更するリクエスト（POST など）では CSRF トークンの照合、または Origin ヘッダの検証を行う。

### 4.4 クライアントの IP アドレスの扱い

- スマートフォンでは、回線の切り替え（モバイル回線と Wi-Fi など）によって IP アドレスが頻繁に変わる。
- 携帯キャリアの CGNAT により、無関係な多数のユーザが同じ IP アドレスを共有する。
- そのため、IP アドレスを認証や制限の主な手段にはしない。
  - セッションを IP アドレスに紐付けない（IP アドレスが変わってもログイン状態を保つ）。
  - IP 単位の回数制限は、正規ユーザを巻き込まないよう緩めの補助にとどめる。攻撃者は IP アドレスを容易に変えられるため、主な対策にもならない。
- 4.1 の Safari の7日制限は、サーバ側の IP アドレス（ページと API が同じサーバか）で決まるため、クライアントの IP アドレスの変化には影響されない。
- 回数制限のカウンターはデータベースのテーブルに置く（TableSpec_Auth.md 4.）。IP アドレスはそのまま保存せず、鍵付きのハッシュ（HMAC）として、窓の長さ（最長1時間）だけ保存し、期限が切れたら削除する。

## 5. ユーザの切り替え

- ユーザはユーザ名を切り替えることで、どのユーザの情報を使用するかを決める。
- サーバはリクエストのたびに、指定されたユーザがログイン中の家族に属しているかを確認する。
- 家族内のユーザ間に認証はなく、家族の誰でもどのユーザにも切り替えられる。これは仕様とする。
- ユーザを削除すると、そのユーザの記録（テスト結果）が、アプリから見られなくなる。利用データ自体は削除されず、研究のために保持される（10.7）。削除前に確認ダイアログを表示し、この内容を明示する。

## 6. アカウントの復旧

- 復旧手段は復旧コードのみとする。
- 以下のケースでも復旧コードでログインする。
  - Cookie が消えた場合
  - 本登録URLがメールアプリ内ブラウザなど、普段と異なるブラウザで開かれた場合
  - iOS でホーム画面に追加して利用する場合（Safari 本体と Cookie が別のため）
  - Android で、普段と異なるブラウザ（Samsung Internet など）からホーム画面に追加して利用する場合（追加に使ったブラウザのデータ領域を使うため）
  - 別の端末で利用する場合
- Android の Chrome では、ホーム画面に追加したアプリ（ショートカット・PWA とも）は Chrome と Cookie・ストレージ・キャッシュを共有するため、Chrome でのログイン状態のまま利用できる。
  - ただし、Chrome の閲覧データやサイトのデータを削除すると、ホーム画面から開くアプリのデータも消える。
- メールアドレスとアカウントの対応はシステム内に存在しないため、メールアドレスによる復旧は行わない。

### 6.1 復旧コード

- 復旧コードは、それだけでログインできる唯一の鍵であり、家族の識別子も兼ねる。
- 総当たりに耐えるよう、十分なエントロピー（128bit 程度）を持たせる。
  - この長さであれば、保存は HMAC-SHA256 などの高速なハッシュで足りる。
- 形式は、Crockford Base32 の25文字（乱数24文字＋チェック用1文字）を、5文字ずつハイフンで区切ったものとする（例：`7K3QM-X9TPA-H2W8R-DF6NB-4CJZ3`）。
  - 文字は数字10種と英大文字22種の32種類（紛らわしい `I`・`L`・`O`・`U` を除く）。紙に書き写すときの取り違えを防ぐため。
  - 乱数部分は 24文字 × 5bit = 120bit となり、128bit 程度の強度を持つ（総当たりは現実的に不可能）。
  - 最後の1文字はチェック用の文字（Luhn mod 32）とする。
    - 1文字の打ち間違いと、隣り合う2文字の入れ替えを、サーバへ送る前にクライアントで検出し、「入力ミスがあります」と知らせる。
    - 打ち間違いを復旧コードの照合の失敗回数（IP 単位の回数制限）に数えないようにするため。
    - チェック用の文字は計算方法が公開されていても、乱数部分の強度は変わらない。
  - 入力時は、ハイフン・空白を除去し、小文字を大文字に揃え、`O` を `0` に、`I`・`L` を `1` に置き換えてから照合する（書き間違いや大文字・小文字の違いでも通るようにするため）。
- 控え方として、画面への表示・コピー・テキストファイルでの保存・印刷を用意し、「控えました」にチェックを付けるまで次の画面へ進めないようにする。
- 総当たりへの主な対策はコードの強度とする（128bit であれば総当たりは現実的に不可能）。
  - システム全体の失敗数を監視する。
  - IP 単位の試行回数制限は、緩めの補助にとどめる（4.4 参照）。
- ログイン中に復旧コードを再発行できるようにする（漏えい・紛失に備えるため）。
  - 再発行時は旧コードを無効化し、操作中の端末以外のセッションを失効させる。

## 7. ログとユーザサポート

- ユーザサポートの範囲は「メールアドレスを入力したのに登録メールが届かない」といった問い合わせへの対応のみとする。
- サポートのため、以下にメールアドレスが残ることを許容する。
  - アプリのエラーログ：メール送信失敗時に、メールアドレスと失敗理由を明示的に記録する。送信成功時は記録しない。仮登録メールと、組織の招待メール（10.5）のいずれも同様とする。
  - メール送信サービスの送信ログ
- サポート時の確認内容：
  - エラーログに該当メールアドレスを含むエラーがないか
  - メール送信サービスが該当アドレスにメールを送信しているか
- サポート案内には「アカウントの復旧は復旧コードのみ」「復旧コードと Cookie の両方を失うと復旧できない」ことを明記する。
- 本登録URLのトークンはフラグメントに含めるため（3.2）、Web サーバのアクセスログには残らない。
  - アクセスログには `/register` へのアクセス（日時・ステータスなど）は残るため、登録の段階ごとの件数の解析は引き続き行える。
  - メール送信サービスの送信ログ（メール本文を保存する場合）とアクセスログを、トークンを手がかりに突き合わせて、メールアドレスとアカウントを対応付けることもできない。
  - ただし、メールのリンク変換（Outlook の安全なリンクなど）を使うメールサービスには、フラグメントを含む URL 全体が渡る。これは防げない。

## 8. 未決事項

- 同一宛先への繰り返し送信の制限についての合意
  - 宛先単位で送信回数を制限するには、メールアドレスのハッシュを短時間（1時間程度、回数制限用のデータベースのテーブルに）保持する必要がある。「保持しない」方針との兼ね合いを確認する。

- 退会・ユーザの削除の後も利用データを保持することの、プライバシーポリシー・退会画面・ユーザ削除画面への記載と、依頼元との合意（10.7）
- 利用データの削除の依頼への対応（退会・ユーザの削除の後は、ユーザ ID から本人を特定できないため、削除を求める場合は、退会・削除の前に依頼してもらう必要がある）
- 所属前に作られた利用データを、組織に参照させるか（現状の設計は、所属中は過去のデータも参照できる。10.4）
- 組織に関する初期値（セッションの有効期限、パスワードの規則など）：TableSpec_Organization.md「9. 未決事項」、ApiSpec_Organization.md「10. 未決事項」

決定済みの事項：

- テーブル設計：TableSpec_Account.md、TableSpec_Auth.md、TableSpec_Organization.md
- Web API：ApiSpec_Auth.md、ApiSpec_Organization.md
- セッションの有効期限：最終利用から365日。前回の更新から1時間以上経過したアクセスで延長する（TableSpec_Auth.md 2.3）
- 回数制限のしきい値：ApiSpec_Auth.md「9. 回数制限」（初期値。利用状況を見て調整する）
- ログにメールアドレスが残ることと、プライバシーポリシーへの記載内容：依頼元と合意済み

- メール確認の目的：依頼元と合意済み（メール確認は「登録のハードル」として残す）
- 復旧コードの形式：Crockford Base32 の25文字（乱数24文字＋チェック用1文字）、5文字ずつハイフンで区切る（6.1）
- 組織（10.）：家族は0または1つの組織に所属する。組織ごとにログインアカウント（ログインID＋パスワード）を1つ発行する。運用担当者（スーパー）の組織は、全ユーザの利用データを参照でき、組織の管理ができる。運用担当者は、失敗回数のロックに加え、パスキーによる確認を必須とする。
- 家族が組織に所属する方法は、組織からの招待メール（10.5、11.）とする。招待先のメールアドレスは保存しない。
- 退会・ユーザの削除の後も利用データを保持し、運用担当者のみが参照できる（10.7）。アカウント情報は削除する。組織が削除された場合、所属していた家族は個人ユーザになる。
- 回数制限のカウンターと WebAuthn の challenge は、データベースのテーブルで持つ（TableSpec_Auth.md 4.）。
- サーバ側は素の PHP で記述し、WebAuthn の検証（web-auth/webauthn-lib など）のために Composer のライブラリを使う。
- 既存の CSV データ（現行の server/ のデータ）の移行は行わない。
- 最初の運用担当者の組織は、運用担当者が SQL で作成する（TableSpec_Organization.md 7.）。

## 9. 今後の検討内容

- 9.1〜9.4 は採用を決定した（2026-11-04）。9.5 は引き続き検討する。

### 9.1 ユーザの切り替えにパスワードロックをかけない理由（現状）

- 家庭内で端末を共有するのは、事実上、親と小さな子供（小学校低学年以下）に限られると想定する。
  - 小さな子供はパスワードを覚えられず、親が毎回入力することになるため、切り替えにパスワードロックはかけない。
- 小学校高学年になると自分専用のスマホを持つ機会が増えるため、そのスマホから別の家族として登録すれば、親に見られることもない。

### 9.2 家族向けの重要な操作の保護（採用）

- 切り替えにロックがないため、子供も親と同じ操作ができる。以下の操作は、誤って行われると影響が大きい。

| 操作 | 誤って行われた場合 |
|---|---|
| 復旧コードの再発行 | 親が控えていたコードが無効になり、他の端末もログアウトされる。新しいコードは子供の画面にしか表示されない |
| 他の端末のログアウト | 親のスマホが使えなくなる |
| ユーザの削除 | そのユーザの記録がアプリから見られなくなる（データは保持され、運用担当者のみが参照できる） |
| スーパーユーザのパスワードの設定・変更・削除 | 親が重要な操作をできなくなる |
| スーパーユーザを他のユーザへ移す | 子供がスーパーユーザになる |
| 退会 | 家族・ユーザの情報が失われる（データは保持され、運用担当者のみが参照できる） |
| 組織への所属 | 家族のすべてのユーザの利用データが、組織に共有される |
| 組織への所属の解除 | 組織への共有が止まる（組織がすでに保存したデータは消えない） |

- 対策として、9.3 のスーパーユーザのパスワード（または 9.4 のパスキー）で、これらの操作を保護する。

### 9.3 スーパーユーザ（採用）

- 家族内のユーザのひとりをスーパーユーザと位置付け、スーパーユーザにのみパスワードを設定できるようにする。
  - 日常の管理操作は覚えやすいパスワードで行い、復旧コードは最後の手段として残す二段構えとする。
- パスワードは家族向けの重要な操作（9.2）の実行時にのみ求める。ユーザの切り替え（スーパーユーザへの切り替えを含む）にはロックをかけない。
  - パスワード入力後は一定時間（5分程度）のみ有効とし、それ以降の重要な操作では再入力を求める。
- パスワードが未設定の家族では、重要な操作の実行時に復旧コードの入力を求める。
- パスワードはログイン済みの端末内での確認にのみ使い、新しい端末からのログインには使わない（ログインは復旧コードのみ）。
  - 短いパスワードでログインできるようにすると、ネットワーク越しの総当たりの対象となり、復旧コードの強度の意味がなくなるため。
- パスワードは4〜64文字とし、文字の種類は問わない（数字だけの PIN も可）。
- パスワードの設定・変更・削除にも確認を求める（未設定の家族では復旧コード、設定済みの家族では現在のパスワード）。子供がパスワードを設定して、親が重要な操作をできなくなるのを防ぐため。
- パスワードは家族に1つとし、スーパーユーザを他のユーザへ移してもそのまま使える。
- パスワードは Argon2id などの低速なハッシュで保存する（復旧コードと違い強度が低いため）。
- 試行回数は家族単位で制限する（IP 単位ではない。4.4 参照）。5回連続で失敗したら15分間ロックする。
- パスワードを忘れた場合は、復旧コードを入力して再設定する（ロック中でも再設定できる）。
- スーパーユーザは家族内にちょうど1人とし、削除できないようにする。
  - スーパーユーザの役割を他のユーザへ移すときも、パスワードの入力を求める。
- 子供が自分のスマホから新しい家族を登録した場合は、その子供自身がその家族のスーパーユーザとなる。

### 9.4 生体認証（パスキー）（採用）

- スーパーユーザはスマホの所有者である可能性が高く、生体認証を設定している可能性も高い。そのため、パスワード入力の代わりに生体認証（WebAuthn のパスキー）も使えるようにする。
  - iOS の Safari、Android の Chrome などのブラウザから利用できる。ネイティブアプリは不要。
  - 生体情報は端末の外に出ない。サーバには公開鍵と識別用の ID のみを保存し、メールアドレスや氏名は不要（ランダムな ID で登録できる）のため、1. の要件に合う。
- パスキーは任意で登録するものとし、パスワードを代わりの手段として残す（アプリ内ブラウザや古い端末ではパスキーが使えない場合があるため）。
  - パスキーの登録は、パスワードが設定済みの家族のみ可能とする。パスキーが登録されている間は、パスワードを削除できない。
  - パスキーの登録・削除は、家族向けの重要な操作（9.2）とする。
  - パスキーは家族あたり10件まで登録できる。
  - 確認時は、生体認証または端末のパスコードによるユーザ検証を必ず求める。
- 注意点
  - 家族共用のタブレットでは、本人を区別できない場合がある。
    - パスキーは端末のパスコードでも確認を通過できるため、子供がタブレットのパスコードを知っていると、子供でも通過できる。
    - Touch ID や指紋認証に子供の指が登録されている場合がある。
    - 親の Apple ID / Google アカウントでサインインしている共用タブレットには、親のパスキーが同期される。
    - パスキーの登録画面で「共用の端末では、パスワードでの確認を推奨します」と案内する。
  - パスキーはサイトのドメインに結び付くため、運用開始後にドメインを変更すると全員が登録し直しになる。

### 9.5 検討事項

- 子供が自分のスマホで新しい家族を登録した場合の、データの引き継ぎ
  - 復旧コードは家族単位のため、親の家族にあるその子供のユーザだけを渡すことはできない。
  - 案A：引き継がない。新しい家族では最初からやり直してもらう。
  - 案B：「ユーザを別の家族へ移す」機能を用意する（例：親の家族で移行用の一時コードを発行し、子供の新しい家族で入力すると、そのユーザが移る）。
- パスキーによるログイン
  - パスキーは復旧コードと同等の強度があるため、新しい端末からのログインに使っても安全。パスキーが同期されている端末であれば、復旧コードなしでログインできるようにすることも検討する。
  - まずは管理操作の確認用のみで始める。

## 10. 組織

### 10.1 位置づけ

- 運用担当者や、利用者に本アプリを提供する教育機関・団体などを「組織」として扱う。組織は、所属する家族のユーザの利用データを参照できる。
- 将来、特定の組織へ利用データを提供する可能性があるため、家族（アカウント）に所属組織を持たせる。
- 家族は、0または1つの組織に所属できる。所属は家族単位で、家族内のすべてのユーザの利用データが対象となる。
- 組織に所属していない家族は、個人ユーザとして扱う。個人ユーザの利用データは、運用担当者のみが参照できる。
- 組織は個人情報を持たない。保持するのは、組織名・ログインID・パスワードのハッシュなどに限る。組織の担当者のメールアドレスは保持しない。

### 10.2 組織の種類

| 種類 | 説明 | 参照できる利用データ | 組織の管理 |
|---|---|---|---|
| 通常の組織 | 招待により家族が所属する組織（教育機関・団体など） | 自組織に所属している家族のユーザの利用データのみ | できない（自組織のアカウントの管理と、招待のみ） |
| 運用担当者（スーパー） | 全体で1つだけ。最初の1つは運用担当者が SQL で作成する | すべてのユーザの利用データ（個人ユーザ・退会した家族・削除されたユーザのデータを含む） | 組織の登録・削除、組織のパスワードの再発行ができる唯一の組織 |

### 10.3 組織のアカウントと認証

- 組織ごとに、ログインアカウントを1つ発行する。組織内の複数の担当者が共有して使う。
- 発行は運用担当者が行う（組織の自己登録はない）。発行時の初期パスワードは1回だけ表示し、最初のログインで変更を求める。
- 認証方式は、ログインID＋パスワードとする（パスワードは Argon2id で保存する）。
  - 家族の認証（4.）とは別の経路とし、別の Cookie・別のセッションのテーブルで管理する。
  - ブルートフォース対策として、パスワードの連続失敗を組織単位で数え、5回でロックする（15分）。IP 単位の制限は、緩めの補助にとどめる（4.4）。
- 運用担当者は、全ユーザの利用データを参照できるため、パスワードに加えて、パスキー（WebAuthn、9.4）による確認を必須とする。
  - ログインは、パスワードの確認の後に、パスキーで確認して初めて完了する。
  - パスキーが未登録の運用担当者の組織（最初のログイン）では、パスキーの登録だけができる状態にして、登録を完了させる。
  - パスキーを紛失した場合は、運用担当者が SQL で登録を削除して、再登録する（TableSpec_Organization.md 7.）。
  - 通常の組織には、現時点ではパスキーを求めない（パスワードのみ）。
- 組織のアカウントは、家族向けの重要な操作（9.2）の確認とは無関係である。

### 10.4 利用データの参照範囲

- 通常の組織は、**現在その組織に所属している家族**のユーザの利用データと、そのユーザ名（ニックネーム）を参照できる。
- 次のデータは、運用担当者のみが参照できる。
  - 個人ユーザ（どの組織にも所属していない家族）のデータ
  - 退会した家族のユーザのデータ
  - 削除されたユーザのデータ
- 参照できる組織は、データを作った時点ではなく、**現在の所属**で決まる。所属の解除・変更、組織の削除により、過去のデータも含めて、参照できる組織が変わる。
- 組織が参照できないもの：復旧コード、スーパーユーザのパスワード、パスキー、端末のログイン（セッション）。
- 組織がすでにダウンロードしたデータは、所属の解除後も組織の手元に残る。これは防げない。

### 10.5 組織からの招待

- 家族が組織に所属する方法は、組織からの招待のみとする。
- 組織の担当者が、組織の画面で、招待先のメールアドレスを入力すると、システムが招待メールを送る。
  - メールアドレスは、システム内に保存しない（仮登録と同じ。3.1）。データベースには、招待トークンのハッシュ・組織・有効期限のみを保存する。
  - 招待メールには、招待URL（トークンを URL のフラグメントに含める。`https://<ホスト>/invite#token=<トークン>`）を記載する。3.2 と同じく、トークンはサーバのアクセスログに残らない。
  - 招待は1通につき1回限り有効とする。有効期限は7日を目安とする。
  - 送信に失敗した場合のログは、仮登録メールと同じ扱いとする（7.）。
- 組織は、誰に招待を送ったか、誰が受け取ったかをシステム上で確認できない（確認できるのは、未使用の招待の件数のみ）。
- 他者のメールアドレス宛ての大量送信に使われないよう、組織単位・システム全体の送信数に上限を設ける（ApiSpec_Organization.md）。組織のログインが必要なため、CAPTCHA は不要とする。
- 招待メールを受け取ったユーザの操作は、11. で定める。

### 10.6 所属の解除と組織の削除

- 家族は、家族向けの重要な操作（9.2）の確認の後に、いつでも所属を解除できる。
- 組織は、所属している家族を、所属から外せる。
- 運用担当者は、組織を削除できる。削除すると、その組織に所属していた家族は、組織に属していない個人ユーザになる。利用データは、そのまま保持される。
- 運用担当者の組織は削除できない。

### 10.7 退会・ユーザの削除と利用データの保持

- 退会（家族の削除）と、ユーザ1人の削除（家族内での削除）のいずれも、**利用データを削除しない**。削除するのは、アカウント情報（家族・ユーザ名・パスキー・端末のログイン・組織への所属）である。
- 利用データには、氏名・メールアドレス・ユーザ名を含めず、ユーザ ID（ランダムな UUID）のみでユーザを区別する。アカウント情報が削除された後は、ユーザ ID から、ユーザ名や家族を特定できない。
- 保持された利用データは、運用担当者のみが参照できる。家族・ユーザ自身は、削除の後は参照できない。
- 退会画面・ユーザの削除画面では、「記録（テスト結果）は削除されず、研究のために保持されること」と「削除の後は、自分では見られなくなること」を明示して、同意を得る（プライバシーポリシーにも記載する。8. 未決事項）。
- 利用データのテーブルは、`users`・`families` への外部キーを持たない（TableSpec_Account.md 5.2）。

## 11. 招待メールを受け取ったユーザの操作

組織から招待メールを受け取ったユーザ（家族の管理をする保護者など）が行う操作を定める。招待の仕組みは 10.5 を参照する。

### 11.1 招待ページを開く

1. メールの招待URL（`https://<ホスト>/invite#token=<トークン>`）を開く。
2. 招待ページの JavaScript が、URL のフラグメントからトークンを読み取り、照合の API に POST の本文で送る（本登録ページと同じ扱い。3.2）。
   - 読み取ったら、`history.replaceState()` で URL からフラグメントを消す。再読み込みに備えて、トークンはそのタブの `sessionStorage` に一時的に保持し、所属の完了時に削除する。
   - 招待ページには、URL 全体を外部に送るアクセス解析などのスクリプトを読み込まない。
   - 照合では、データベースを変更しない（メールのリンクスキャナーが URL を開いても、招待が消費されないようにするため）。
3. 招待が有効なら、組織名と、所属したときに共有される内容（11.2）を表示する。無効・期限切れ・使用済みなら、「リンクが無効または期限切れです。招待した組織に、もう一度招待を依頼してください」と表示する。

### 11.2 所属する前に確認すること（画面に表示する内容）

- 所属すると、組織が、**家族のすべてのユーザ**の利用データ（テスト結果）と、ユーザ名（ニックネーム）を参照できるようになる。
- 所属する前に作られたデータも、参照の対象になる（10.4）。
- 組織が参照できないもの：復旧コード、パスワード、端末のログイン。
- 所属は、あとから解除できる。解除すると、組織はそれ以降、データを参照できなくなる。組織がすでにダウンロードしたデータは、消えない。

### 11.3 まだ本アプリに登録していない場合（新規登録）

1. 招待ページで「新しく登録する」を選ぶ。
2. 11.2 の内容に同意すると、ユーザ名の入力画面（3.2 の 2.）へ進む。
   - 招待メールが届いたこと自体が、メールアドレスの確認になるため、仮登録のメール送信は不要とする。
3. 1〜4名のユーザ名を入力して登録する。「1人目は家族の管理をする人（保護者など）にしてください」と案内する（3.2）。
   - 登録の完了以降は、通常の本登録（3.2 の 3.〜5.）と同じ。作られる家族は、招待した組織に所属した状態になる。
4. 復旧コードを控える。
- 招待は1回限り有効である。ユーザ名の入力の途中で離脱した場合は、有効期限内であれば、同じ URL から再開できる。

### 11.4 すでに本アプリに登録している場合（所属の追加）

1. 招待ページで「登録済みの家族に所属を追加する」を選ぶ。
2. この端末でログインしていなければ、復旧コードでログインする（6.）。
3. 家族向けの重要な操作の確認（9.3、9.4）を行う（スーパーユーザのパスワードまたはパスキー。パスワードが未設定の家族は復旧コード）。子供が誤って、または勝手に所属させることを防ぐため。
4. 組織名と共有される内容（11.2）を確認して、「所属する」を押す。
- すでに別の組織に所属している場合は、「現在の組織（組織名）から、この組織に移ります。現在の組織は、データを参照できなくなります」と警告し、同意を得る。
- すでに同じ組織に所属している場合は、何も変更せず、招待も消費しない。

### 11.5 心当たりのない招待メールを受け取った場合

- 何もしなくてよい。招待は、有効期限（7日）で無効になる。招待のURLを開いただけでは、所属は成立しない。
- 組織名に心当たりがない場合は、その組織に連絡する。システムのサポートでは、招待メールの送信先を確認できない（メールアドレスを保存していないため）。

### 11.6 所属した後

- 設定画面に、所属している組織名を表示する。
- 所属は、家族向けの重要な操作の確認の後に、いつでも解除できる（10.6）。
