# 用語集

`server2` の画面（UI）・仕様書・コード（API・データベース）で使っている用語を、一か所にまとめたもの。**今後、用語を修正するとき（言い換え・統一）に、影響の範囲を見落とさないため**の資料である。

- 用語の定義の正は、基本方針（BasicPolicy.md）と各仕様書。この文書は、それらの用語を横断して、「どの言葉が、画面・仕様書・コードで、何と呼ばれているか」を対応づける。
- 調査した時点（2026-11-16）の実装・仕様書に基づく。**同日、用語「組織」を「所属」に改めた**（識別子も変更。旧称は、各表の備考と 4. に書いた）。用語を変えたときは、この文書も更新する（5. を参照）。

## 0. 表の見方

| 列 | 内容 |
|---|---|
| 用語 | この文書での正式な呼び方（仕様書の表記） |
| 意味 | 何を指すか |
| 画面の表記 | 利用者に見える文言（`public/app/` の画面）。「—」は、画面に出ない |
| コード・DB・API | 識別子（テーブル名・列名・JSON のキー・エラーコード・クラス名など）。変更は、画面の文言より影響が大きい |

「画面の表記」は、利用者（ユーザ・所属・運用担当者）を区別せずにまとめた表記。**利用者ごとの違いは、2. にまとめている**。

画面の文言は HTML・JS に直接書かれている。識別子の変更は、API の互換性・データベースの再作成・テストの修正を伴う。**識別子は、原則として変えない**（変える場合は、事前に相談する）。

## 2. 利用者ごとの用語の使用状況

同じ用語でも、画面を見る人によって、使い分ける（言い換える）ことがある。そこで、**どの画面を、誰が見るか**を整理し、用語ごとに、利用者別の実際の文言を並べる。

### 2.1 利用者の区分と、対応する画面

| 区分 | 誰か | 画面（`public/app/`） | 文言の置き場所 |
|---|---|---|---|
| **ユーザ側** | 家族・ユーザ（本アプリを使う人）。招待メールを受け取った人を含む | ホーム（ログインしていない・ユーザの選択・各ユーザのホーム・家族の編集）、ログイン、仮登録（`signup/`）、本登録（`register/`）、招待（`invite/`） | `index.html`、`home.js`、`login/`、`signup/`、`register/`、`invite/`、`registration-ui.js` |
| **所属側** | 通常の所属の担当者 | 招待、所属している家族、利用データ（準備中）、アカウント | `console/invitations.js`、`console/members.js`、`console/account.js` |
| **運用担当者側** | 運用担当者 | 家族の管理、所属の管理、パスキーの管理（この3つは、運用担当者のみ） | `console/families.js`、`console/belongings.js`、`console/passkeys.js` |
| 所属・運用担当者の**共通** | 通常の所属と、運用担当者の両方 | ログイン、パスキーの確認・登録、ログイン後の枠（左のメニュー・ホーム）、パスワードの再確認のダイアログ | `console/index.html`、`console/blg.js` |

- 所属側と運用担当者側は、**同じページ**（`public/app/console/`）で、ログインアカウントの種類（`isSuper`）に応じて、メニューや文言を切り替えている。運用担当者は、所属側のメニュー（招待・所属している家族・利用データ・アカウント）も使える。
- すでに、種類で文言を切り替えている箇所:
  - 左上のバッジ: 「運用担当者」／「所属」（`blg.js` の `renderShell`）
  - ホームの「種類」: 「運用担当者（全ユーザの利用データを参照でき、所属を管理できます）」／「所属」（`blg.js` の `renderHome`）
  - メニューの区切り: 「運用担当者のみ」（`blg.js`）
  - 「利用データ」の説明: 「すべてのユーザの…」／「この所属先に所属している家族のユーザの…」（`blg.js` の `MENU`）
- ユーザ側の画面には、「運用担当者」「個人ユーザ」「所属から外す」「パスキー」は、出ない。

### 2.2 用語ごとの、利用者別の文言

「—」は、その利用者の画面に出ない。（ ）の中は、画面での実際の文言の例。

### 2.3 利用者別に使い分けるときの注意

- **同じ操作でも、利用者ごとに、動作主が違う。** 「所属の解除」は、ユーザ側（家族が自分で）・所属側（自所属から外す）・運用担当者側（任意の家族）で、誰が・どの範囲で行うかが違う。用語を分けるなら、利用者ごとの言い方を、ここに書く。
- **「パスワード」「アカウント」「確認」は、利用者によって、指すものが違う**（上の表）。所属側と運用担当者側は同じページを共有しているため、片方の言い方だけを変えるときは、`isSuper` で切り替える必要がある。
- ユーザ側の画面は、所属の担当者や運用担当者の用語（運用担当者・個人ユーザ・パスキー）を、利用者に見せない。この方針は、維持する。
- 招待ページ（`invite/`）は、ユーザ側の画面だが、**所属の用語**（所属名・所属）を表示する。所属が登録した名前を、そのまま見せる。

## 5. 用語を変更するときの手順

1. この文書で、変更する用語の行を探す。「画面の表記」と「コード・DB・API」のどちらを変えるか決める（3. の規則のとおり、識別子は原則変えない）。
2. 画面の文言は、次を検索して、すべて置き換える。

   ```bash
   cd server2
   grep -rn "<用語>" public/app src docs README.md tests
   ```

   - 画面: `public/app/**/*.html`、`public/app/**/*.js`
   - サーバのメッセージ・コメント: `src/`
   - 仕様書: `docs/*.md`、`README.md`
   - テスト: `tests/`（メッセージの文言を検証している箇所がある）
   - 「〜を」「〜の」など、助詞が付くため、単純な置換で文が崩れないか、読んで確認する。
3. 識別子を変える場合は、データベースの DDL（`docs/sql/`）・`TableSpec_*.md`・API の仕様書・JS のクライアント（`public/js/uectst-api/`）・テストを、すべて同時に変える。開発用のデータベースは、作り直す。
4. 変更したら、PHPUnit（`vendor/bin/phpunit`）と JS のテスト（`npm test`）を実行する。
5. この文書の該当する行と、2. の利用者別の表、4. の揺れの一覧を、更新する。
